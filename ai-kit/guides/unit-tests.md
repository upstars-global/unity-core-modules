## Полиси по юнит тестам

### Главная цель

- Довести покрытие юнит тестами до 60% функционала наших репозиториев.

### Обязательные правила

- Новый функционал должен выходить с юнит тестами.
- Изменённый функционал должен сопровождаться обновлением существующих тестов или добавлением новых.
- Тесты должны покрывать только логику в рамках текущей задачи, без лишнего расширения скоупа.
- Предпочтение отдаём детерминированным тестам без реальных сетевых запросов и нестабильных внешних зависимостей.

### Если тесты требуют большого рефакторинга

Если для корректного unit test покрытия нужен серьёзный рефакторинг, который увеличивает scope задачи более чем на 15%,
то:

1. Не расширяем текущую задачу до большого архитектурного рефакторинга.
2. Создаём отдельную задачу в epic [UN-2429](https://upstars.atlassian.net/browse/UN-2429) на рефакторинг.
3. Пишем `TODO` в затронутом файле с ссылкой на созданную задачу.
4. В текущей задаче фиксируем максимально безопасное покрытие без выхода за согласованный scope.

### Зачем и для чего нужны юнит тесты в приложении на Vue 3

Юнит тесты — это тесты, которые проверяют работу отдельных компонентов или методов в аппе. Зачем они нужны:

1. **Снижение багликеджа:** Юнит тесты помогают находить и устранять ошибки на этапе разработки до того
   как они попадут в тест или на прод
2. **Устойчивость к изменениям:** Тесты позволяют легко обнаруживать проблемы, которые могут возникнуть
   после доработок или рефакторинга кода
3. **Документация:** Юнит тесты это своего рода живая документация, которая показывает, как должен вести себя компонент.
4. **Ускорение разработки:** С тестами можно быстро проверять работу компонентов вместо того, чтобы вручную тестировать
   их после каждого изменения

### Что, как и зачем мы тестируем

#### 1. **Рендеринг компонента**

- **Что:** Отображение темплейта и его содержимого в соответствии с данными и пропсами
- **Как:** Использовать `mount`, проверить текст и элементы через `wrapper.text()` и `wrapper.find()`
- **Зачем:** Убедиться, что компонент отображается правильно
- **Пример:**
  ```javascript
  const wrapper = mount(AdditionalButton, {
    props: { title: 'Deposit' }
  });
  expect(wrapper.text()).toContain('Deposit');
  // на кнопке будет написано Deposit
  ```

  ```javascript
  const wrapper = mount(AdditionalButton);
  expect(wrapper.find('button.additional-button').exists()).toBe(true);
  // кнопка отрендерилась и существует (класс позволяет убедиться что кнопка наша)
  ```

#### 2. **Реактивность данных**

- **Что:** Изменение данных и ререндер
- **Как:** Изменить состояние компонента и проверить, как это отразилось на темплейте
- **Зачем:** Убедиться, что компонент ререндерится правильно при изменении данных
- **Пример:**
  ```javascript
  const wrapper = mount(AdditionalButton, {
    props: { title: 'Initial Title' }
  });
  await wrapper.setProps({ title: 'Updated Title' });
  expect(wrapper.text()).toContain('Updated Title');
  // текст на кнопке поменялся, потому что поменялись пропсы
  ```

#### 3. **Эвенты**

- **Что:** input, click, change и другие эвенты
- **Как:** Использовать `trigger` для имитации эвентов и проверить, что они вызывают нужные действия
- **Зачем:** Убедиться, что компонент правильно реагирует на действия юзера
- **Пример:**
  ```javascript
  const wrapper = mount(AdditionalButton);
  await wrapper.find('button').trigger('click');
  // имитируем нажатие на кнопку
  ```

  ```javascript
  const onClickMock = jest.fn();
  const wrapper = mount(AdditionalButton, {
    listeners: { click: onClickMock }
  });
  await wrapper.find('button').trigger('click');
  expect(onClickMock).toHaveBeenCalled();
  // проверяем что метод, привязаный к нажатию на кнопку отработал (юнит тест самого метода может и должен быть отдельным тестом)
  ```

#### 4. **Методы**

- **Что:** Логика которая содержится в методах компонента
- **Как:** Вызвать метод и проверить его ретерн или изменения стейта
- **Зачем:** Убедиться что методы работают правильно и делают то что нужно
- **Пример:**
  ```javascript
  const wrapper = mount(AdditionalButton);
  const methodResult = wrapper.vm.someMethod(); // вызов метода
  expect(methodResult).toBe('expectedResult'); // проверка результата
  ```

#### 5. **Пропсы**

- **Что:** Правильность обработки и отображения пропсов
- **Как:** Пробросить пропсы в компонент и проверить как они отображаются
- **Зачем:** Убедиться что компонент корректно использует переданные ему пропсы
- **Пример:**
  ```javascript
  const wrapper = mount(AdditionalButton, {
    props: { title: 'Button Title', disabled: true }
  });
  expect(wrapper.attributes('disabled')).toBe('disabled');
  // кнопка будет задизейблена
  ```

  ```javascript
  const wrapper = mount(AdditionalButton, {
    props: { fullWidth: true }
  });
  expect(wrapper.classes()).toContain('additional-button--full-width');
  // кнопка растянется (не проверяем визуал, мы проверяем только логику) 
  ```

#### 6. **Слоты**

- **Что:** Отображение контента в слотах
- **Как:** Передать содержимое через слот и проверить как оно отображается
- **Зачем:** Убедиться что дочерний контент отображается правильно
- **Пример:**
  ```javascript
  const wrapper = mount(SomeButton, {
    slots: { default: '<span>Slot Content</span>' }
  });
  expect(wrapper.html()).toContain('Slot Content');
  // Slot Content будет там где расположен слот. Проверяем что он существует 
  ```

#### 7. **Жизненные циклы**

- **Что:** Поведение которое есть в лайсайкл хуках компонента
- **Как:** Проверить вызовы методов в лайфсайкл хуках
- **Зачем:** Убедиться, что компонент правильно создается и уничтожается
- **Пример:**
  ```javascript
  const createdSpy = jest.spyOn(AdditionalButton.methods, 'createdMethod');
  mount(AdditionalButton);
  expect(createdSpy).toHaveBeenCalled();
  // моделируем, что createdMethod вызывается в хуке created, маунтим компонент и проверяем был ли вызван метод
  ```

  ```javascript
  const destroyedSpy = jest.spyOn(AdditionalButton.methods, 'beforeDestroyMethod');
  const wrapper = mount(AdditionalButton);
  wrapper.unmount();
  expect(destroyedSpy).toHaveBeenCalled();
  // то же самое но с beforeDestroy
  ```

#### 8. **Взаимодействие с другими компонентами**

- **Что:** Взаимодействие компонента с дочерними компонентами
- **Как:** Проверить передачу пропсов и обработку событий от дочерних компонентов
- **Зачем:** Убедиться что компоненты правильно работают вместе
- **Пример:**
  ```javascript
  const wrapper = mount(AdditionalButton, {
    props: { icon: 'check' }
  });
  const iconComponent = wrapper.findComponent(FeIcon);
  expect(iconComponent.props('icon')).toBe('check');
  // маунтим кнопку и передаем в нее иконку, проверяем что дочерний FeIcon существует и в нем нужная иконка
  ```

#### 9. **Обработка ошибок**

- **Что:** Реакция компонента на ошибки или негативные данные
- **Как:** Создать ситуации с ошибками и проверить, как компонент их обрабатывает
- **Зачем:** Убедиться, что компонент не ломается при возникновении ошибок
- **Пример:**
  ```javascript
  jest.mock('@controllers/Logger', () => ({
    error: jest.fn(),
  })); // мокаем логгер
  
  console.error = jest.fn(); // мьютим ошибки в консоли
  mount(AdditionalButton, {
    props: { title: null } // передаем плохой пропс
  });
  expect(log.error).toHaveBeenCalled(); // проверяем, что обработали и залогали ошибку
  ```

### Что мы НЕ тестируем

- **Стилизация компонентов:** Внешний вид (css, анимации, миксины и тд). Стилизация не влияет на логику и тестируется
  руками и/или скриншотницей
- **Работа 3rd-party:** внутренняя логика сторонних библиотек (например пинья, капча, dayjs) или внешние компоненты -
  этим занимаются разработчики самих 3rd-party
- **Производительность:** Юнит тесты не предназначены для тестирования производительности (например трекинга колва
  ререндеров)
- **Интеграция с сервером:** Юнит тесты не проверяют работу API или серверных взаимодействий, это работа для
  интеграционных тестов и/или Е2Е
- **Кроссбраузерность/кроссдевайсность:** это задача QA
